## 5. Files a C++ bot needs to build

`tools/benchmark.py` copies only `bots/<bot>/src` into `<output>/inputs/<bot>/src`, outside
the workspace, and `run-batch` builds it there:

```
python tools/benchmark.py starter starter --maps 00rows 00lanes --jobs 4 --output <scratch>/bench1 \
  --json --no-progress --color never --runner .venv\Scripts\cambc.exe     (PYTHONUTF8=1)
-> 4 games, 0 errors, exit 0, 40 s including build
```

The build uses the workspace's `cmake/CMakeLists.txt` (`GLOB_RECURSE ${BOT_DIR}/src/*.cpp`),
`sdk/cpp` (include dir) and the toolchain in the user cache. **Bots: only sources (matches).**
The workspace-level `cmake/CMakeLists.txt` is a build input: it belongs in the manifest and
outside agent scope. `.h`/`.hpp` files in subdirectories would be picked up by the
recursive glob; §8 forbids subdirectories anyway. The CLI binary contains the string
`build scripts are forbidden`.

## 6. SDK headers

(`wasm32-wasip1/eh/c++/v1`, 191 entries including internal `__*` dirs). §8.3 assumed

## 9. Timing and concurrency (Actions part)

| | run 1 | run 2 |
|---|---|---|
| `nproc` | 4 | 4 |
| `pip install cambc` | 5 s | 7 s |
| first build of 2 bots (cold toolchain download included) | 14 s | 17 s |
| 4 games, `--jobs 4` (incl. per-suite build) | 12.2 s | 17.2 s |
| 2 games, `--jobs 2`, `00eight` | 6.9 s | 8.4 s |

So t ≈ **6–8 s per game per core** for 2000-round starter-level games (the PC needs 30–40 s on Windows).
Stronger bots that use their full fuel may be slower, so M1 re-measures with real shards.
Concurrency: all 22 one-job "hold" slots (3 minutes each) started within 2 s of each other and
ran at the same time (peak 22), alongside the 2 game jobs. So at least 22 concurrent jobs, more than the
plan's ~20; the real cap was not reached and is not known. `evo-env-test.yml` (same push): setup script **36 s**, SessionStart check **11 s**, both passed.

**§14 recomputed** at t = 7 s, 4 cores: a generation of about 1,800 games ≈ 1800 × 7 / 4 / 60 ≈
**53 runner-minutes** plus about 1 minute of setup per shard (45 shards of 40 games ≈ 45 min) ≈ 100 runner-minutes.
Wall-clock with about 20 jobs in parallel: under 10 minutes. With shards of 40 games at about 70 s each, setup
dominates; `shard_games` could go to 200 (≈ 6 minutes of play per shard) in M1. Owner decides at M1.

## 10 (partial, from the docs, no session). Choosing the environment

## 11 (first attempt). Setup script failed in the cloud

Session `session_01UXqFVEGzUDbebuGuJ7d1a6` (the approved probe) stopped in the environment's
setup script. The owner saw only pip's warning in the app:
`WARNING: Running pip as the 'root' user can result in broken permissions ...`. That warning
alone does not fail pip (exit 0), so the failing command is not known. The old script sent cambc's stdout to
`/dev/null`, and the app showed no later line. The session pushed no branch.

What it shows: the setup script **runs as root** with the system `pip` (unlike Actions' `setup-python`).
Fix (`c010278`): `setup.sh` logs every step and names the failing command (`trap ERR`) to stdout and
`/opt/evo-setup.log`, uses `python3 -m pip` (falling back to `--break-system-packages` for PEP 668),
sets `PIP_ROOT_USER_ACTION=ignore`, and links `cambc` onto `PATH` if the scripts dir is not on it.
`evo-env-test.yml` gained an `env-root` job that runs both scripts as root in `ubuntu:24.04`
with the system Python, which is closer to the cloud VM.
